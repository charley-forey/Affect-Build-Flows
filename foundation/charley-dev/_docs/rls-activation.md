# Row-level security - activation runbook

Both Direct Lake models (**Affect Project Report**, **Project Quality Plan**) ship two roles,
generated by `_local/deploy_model.py` (`roles_tmdl`) and reused by `deploy_model_qc.py`:

| Role | Filter | For |
|---|---|---|
| **Project Viewer** | Deny by default. Rows only for projects granted in `man_ProjectAccess` | PMs, superintendents, Q-Team |
| **Portfolio Viewer** | None | Executives and finance who need every project, UNMATCHED rows and blank-project data gaps |

**Nothing changes for today's users.** RLS applies only to identities *without Write* on the
model: workspace **Viewers** and **App** audiences. Admin / Member / Contributor users bypass
it, whatever the roles say. The roles are dormant until someone is shared the content as a
Viewer. Do that only after the steps below.

## How Project Viewer decides

The filter is chosen per table from the table's published columns, so a new table is covered
without anyone remembering to:

- **Has `ProjectKey`**: `Table[ProjectKey] IN <granted projects>`, set on every such table
  individually, not only on `dim_Project`. A NULL, unmapped (`fct_ApInvoice`, `dq_DataGap`)
  or `UNMATCHED` key is never in the granted set, so it never leaks through the blank member.
- **Has `VendorKey` but no `ProjectKey`** (`dim_Vendor`, `dim_VendorCrosswalk`,
  `fct_VendorInsurance`): only vendors that appear on a granted project.
- **In `PUBLIC_TABLES`** (dates, cost codes, status vocabularies, scorecard config, QC seeds,
  pipeline heartbeat): unfiltered.
- **Anything else**: `FALSE ()`. The table is empty for the role until it is classified.
- **`man_ProjectAccess`**: the user's own grant rows only. The table is also hidden from
  report view.

A grant is live when `UserPrincipalName = USERPRINCIPALNAME()` (lower-cased on both sides)
and `EffectiveFrom <= TODAY() <= EffectiveTo`. A blank bound is open, and `TODAY()` is the
service's UTC date. `ProjectKey = ALL` grants every real project, but still **not**
`UNMATCHED` or blank-project rows. Those rows pool data nobody could attribute, so they
belong to Portfolio Viewer.

**Fail closed.** Silver (`30_manual_silver.sql`) rejects an unknown project, a malformed UPN,
an inverted date window, or two conflicting rows for one (user, project). A rejected grant
grants nothing, and the reason appears on the DQ page (`dq_DataGap`, "Rejected manual
entry"). The DQ gate also fails on a gold grant to a non-project or a non-normalised UPN.

## Direct Lake requirement - read this before sharing with anyone

Checked against Microsoft Learn, *Integrate Direct Lake security*
(learn.microsoft.com/fabric/fundamentals/direct-lake-security-integration, updated
2026-09-09). Both models are **Direct Lake on OneLake** (`AzureStorage.DataLake`
expression), which gives three findings:

1. **Model RLS is supported on Direct Lake on OneLake** and stays in memory. There is no
   DirectQuery fallback on OneLake, and so no fallback that could bypass the role.
2. **With the default SSO connection, every viewer needs *Read + ReadAll* on
   `CD_Gold_Lakehouse`**, or a OneLake security role. That is the problem: a user who can read
   the lakehouse can read every row through the SQL endpoint, a notebook or OneLake. Model RLS
   "only applies within the scope of that model". Microsoft's own guidance is to use model RLS
   *"when report consumers aren't granted permission to query the lakehouse ... and the cloud
   connection uses a fixed identity instead of SSO."*
3. So the **required setting** is a **fixed identity** with SSO **off**:
   - Create a shareable cloud connection to OneLake. Authenticate it with a **Service
     Principal** or **Workspace Identity** (OAuth 2.0 also works but ties it to a person; key
     and SAS are not supported for Direct Lake).
   - Grant that identity *Read + ReadAll* on `CD_Gold_Lakehouse`. Contributor on the workspace
     also works.
   - In each model: **Settings -> Gateway and cloud connections -> Cloud connections**, map
     `DirectLake - CD_Gold_Lakehouse` to that connection, and leave **Single sign-on
     (Microsoft Entra ID) unchecked**. With SSO on, the connection is used only for framing
     and queries still check the viewer's own lakehouse access.
   - **Do NOT grant viewers any permission on `CD_Gold_Lakehouse`** or the workspace, and add
     them to no OneLake security role. Share the App only.
   - The model **owner** still needs read on the lakehouse for framing (reframe fails with
     "access was denied" otherwise).

OneLake data access roles are **not needed** in this design. Enabling OneLake security on the
lakehouse would add a second layer: OneLake roles are unioned and then intersected with the
model roles, and models that rely on OneLake security do not support backup. Leave it off
unless the lakehouse itself must be shared with restricted users.

## Activation steps

1. **Lock down the register.** In SharePoint, break permission inheritance on **CD Project
   Access** and allow edits only to the data-platform owners. Anyone who can edit that list
   can grant themselves every project. The CSV path (`Files/_manual/project_access.csv` in
   `CD_Bronze_Lakehouse`) is writable only by workspace Contributor+, who bypass RLS anyway.
2. **Provision.** Re-run `01-ingestion/Manual/provision-sharepoint.ps1`. It is idempotent and
   adds the **CD Project Access** list and the `ALL` item in **CD Projects**.
3. **Populate.** One row per user per project: `UserPrincipalName` (the Entra UPN, e.g.
   `jane.doe@affectbuild.com`, not a display name or alias), `ProjectKey` (lookup, or `ALL`),
   `Role` (informational), and optionally `EffectiveFrom` / `EffectiveTo`. For CSV, download
   `Files/_manual/_templates/project_access.csv`.
4. **Build.** Run the nightly chain, or `deploy_manual.py --apply` -> silver -> gold. Confirm:
   `man_ProjectAccess` has the expected rows, and the DQ page shows no
   `cd_silver_man_project_access` rejects. Any reject is someone who will see an empty report.
5. **Deploy the models.** Run `python _local/deploy_model.py --apply` and
   `python _local/deploy_model_qc.py --apply`. Gold must be rebuilt first: `introspect()`
   refuses to generate a model whose table (`man_ProjectAccess`) is missing from
   `gold_schema.json`. Check that `definition/roles/Project Viewer.tmdl` and
   `Portfolio Viewer.tmdl` were written.
6. **Bind the fixed identity** (see above) on both models, with SSO off. Reframe once.
7. **Assign members.** For each model: **Security** -> role -> add **Entra security groups**,
   not individuals (e.g. `SG-Reporting-ProjectViewers`, `SG-Reporting-PortfolioViewers`).
   A user in both roles gets the union, which is effectively Portfolio. Keep the groups
   disjoint. **Unverified:** whether `updateDefinition` preserves members assigned in the
   service. The generated definition carries no `member` lines. After every
   `deploy_model*.py --apply`, re-open Security and confirm the groups are still there. Groups
   make re-adding a two-click fix.
8. **Share through the App** with Viewer-only audiences: publish or update the workspace App
   and add the same security groups as audiences. Do not add these users to the workspace, or
   they become Contributor+ and bypass RLS.
9. **Test before telling anyone** (below).

## Testing

**View as role (service).** Model -> Security -> `...` -> **Test as role**. Pick *Project
Viewer* and **Now viewing as: another user**, then enter a UPN from the register. Check that
the project slicer lists only granted projects, that `UNMATCHED` is absent, and that the Data
Gaps and AP pages show no blank-project rows. Repeat with a UPN that has no grant: every
visual over project data must be empty. Repeat with *Portfolio Viewer*: everything must show.

**DAX via executeQueries with impersonation.** The caller needs Build/Write on the model. The
`impersonatedUserName` field applies RLS as that user, which is the same as
`EFFECTIVEUSERNAME` over XMLA:

```http
POST https://api.powerbi.com/v1.0/myorg/groups/{workspaceId}/datasets/{datasetId}/executeQueries
{
  "queries": [{ "query": "EVALUATE SUMMARIZECOLUMNS ( dim_Project[ProjectKey], \"Rows\", COUNTROWS ( fct_BudgetLine ) )" }],
  "serializerSettings": { "includeNulls": true },
  "impersonatedUserName": "jane.doe@affectbuild.com"
}
```

Run the queries below as a granted user, as an ungranted user, and without impersonation (the
baseline):

```dax
// 1. Granted projects only; no UNMATCHED, no blank.
EVALUATE VALUES ( dim_Project[ProjectKey] )

// 2. Deny-by-default for unattributed rows: both must be 0 for Project Viewer (Model A; on
//    the PQP model drop the fct_ApInvoice column).
EVALUATE ROW (
    "BlankGaps", COUNTROWS ( FILTER ( dq_DataGap, ISBLANK ( dq_DataGap[ProjectKey] ) ) ),
    "UnmappedAp", COUNTROWS ( FILTER ( fct_ApInvoice, ISBLANK ( fct_ApInvoice[ProjectKey] )
                                        || fct_ApInvoice[ProjectKey] = "UNMATCHED" ) ) )

// 3. The user sees only their own grants.
EVALUATE man_ProjectAccess
```

Over XMLA (SSMS / DAX Studio), connect with `EffectiveUserName=jane.doe@affectbuild.com;Roles=Project Viewer`
on the connection string and run the same queries.

Record the results in `_docs/validation-history/` like the other live checks.

## Rolling back

Remove the role members. The definitions can stay: an unassigned role changes nothing. To
remove the roles entirely, delete `roles_tmdl` from `write_files`, redeploy, and confirm in Security that they are gone.
